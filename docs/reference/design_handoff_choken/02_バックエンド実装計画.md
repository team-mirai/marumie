# 02 バックエンド実装計画

`docs/backend-architecture-guide.md` のレイヤードアーキテクチャ・依存ルール（dependency-cruiser で自動検証）に完全準拠する。

## Bounded Context

| アプリ | コンテキスト | 責務 |
|---|---|---|
| admin | **research-fund**（新設） | 調研費の帳簿管理・スキャンパイプライン・公開ワークフロー |
| webapp | **research-fund**（新設） | 公開ページ向けの読み取り専用集計 |
| 共通 | shared | Politician / Party / ResearchFundAccount など両アプリで使うモデル・リポジトリ |

- research-fund → shared の依存のみ許可。data-import / report / auth への直接依存は禁止（既存ルールどおり）
- politicians / memberships / accounts は webapp からも読むため **shared** に置く（政党テーブルは新設せず既存 political_organizations を親に使う）。books / entries / scan / prompts / groups は admin 側が書き webapp 側が読むので、モデルは shared、リポジトリは各アプリの research-fund コンテキストに分けるのが既存の Transaction / PoliticalOrganization の前例に沿う

## LLM 抽出（スキャンパイプライン）

既存の前例：`report/infrastructure/llm/vercel-ai-gateway.ts`（`@ai-sdk/anthropic` + `generateText`）。research-fund では **`generateObject` + Zod スキーマ**で構造化する。

```
interface ReceiptExtractionGateway {
  extract(params: {
    document: { bytes: Uint8Array; mime: string };  // 画像 or PDF
    officePrompt: string;                            // 議員室ごとのプロンプト（DBの有効版）
    model?: string;                                  // 既定 "claude-opus-4-1"
  }): Promise<ExtractedReceipt>;
}

// ExtractedReceipt（domain/models/extracted-receipt.ts のZod）
{ date: "YYYY-MM-DD",
  items: [{ item: string, amount: number, category_key: string,  // 調研費カテゴリ21分類 or "needs-review"
            note?: string, split_group?: string }] }
```

- プロンプトは「**自動生成部**（出力スキーマの指示・カテゴリ21分類の語彙と定義文。Zodスキーマと分類定義の定数からコードが組み立てる。ユーザー編集不可）＋**議員室プロンプト**（DB管理・管理画面から編集）」の2層。**自動生成部はコード、議員室プロンプトはDB**
- split_group の分割粒度規則（例: カテゴリ・項目が異なる明細は行を分ける／同一品の複数購入はまとめてよい）や「迷ったら needs-review」などの**ポリシーは自動生成部に入れない**。議員室プロンプトの**デフォルトテンプレート**（初期版の内容。コードの定数として提供）に置き、利用者が編集できるようにする
- プロンプト編集画面では自動生成部を折りたたみ等で**参照できる**（読み取り専用。「実際に何が送られるか」を見せる）
- `category_key: "needs-review"` は draft 仕訳を作りつつ科目未確定として確認画面で目立たせる
- 1書類から複数明細 → 複数仕訳（同一 document_id・同一 split_group）
- raw_json はジョブに保存（監査・プロンプト改善用）。test-prompt は同じゲートウェイを呼ぶが永続化しない

## ジョブ実行方式（設計判断）

キュー基盤（外部ワーカー）は導入しない。Vercel サーバーレスの制約下で：

1. `create-scan-batch` は Storage 保存＋ `queued` ジョブ作成まで（速い）
2. `process-scan-jobs` action が queued を古い順に **1〜3件だけ** 処理して返す（1件あたり LLM 呼び出し1回。タイムアウト内に収まる件数に留める）
3. クライアント（スキャン画面）が「未処理が残っている間」`process-scan-jobs` を繰り返し呼ぶ＋ジョブ一覧をポーリング表示

これで30枚バッチも順次消化できる。将来 QStash / cron に差し替える場合も usecase はそのまま使える。**同時実行の排他**（running が既に一定数あれば処理しない）を usecase に入れること。

## テナントスコープ（権限）

- 利用者は各議員室スタッフ。既存 auth の `user_tenant_memberships` を使い、**全 loader / action で politician.tenant_id と現在ユーザーのテナントの一致を検証**する（report コンテキストの counterpart と同じパターン）
- 党本部ロール（複数議員を見る）は既存 role の範囲で。追加のロール設計は Out of scope

## エラーハンドリング・テスト

- ガイド 6.3 に従う。ドメインのバリデーションは `{ status: "invalid", errors: [...] }` 形式、コードは `RF_` 接頭辞（例 `RF_UNBALANCED_ENTRY`, `RF_INVALID_CATEGORY`, `RF_ALREADY_PUBLISHED`）
- ユニットテストは `admin/tests/server/contexts/research-fund/` に src と同階層で。**重点**: journal-posting（3パターン＋貸借一致）、grant-schedule（当選月起点・按分）、extracted-receipt（不正JSONの正規化）、publish-rules、sankey-aggregator（法定区分への集計が科目マスタのマッピングと一致。旧spec §6の検算値は旧15分類ベースのため参考値扱い）
