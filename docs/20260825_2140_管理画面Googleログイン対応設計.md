# 管理画面 Google ログイン対応設計

## 目的

チームみらいがホスティングする admin（管理画面）の利用者が、パスワードの発行・管理をせずに組織の Google アカウント（team-mir.ai ドメイン）でログインできるようになるため。

あわせて、本アプリケーションは OSS として他団体にも利用されるため、既存のメール/パスワード認証（招待・パスワードリセット含む）を一切変更せず、環境変数によって利用する認証プロバイダーを選択できるようにする。

## 背景・現状

- 認証基盤は Supabase Auth。認証操作は `AuthProvider` インターフェース（`contexts/auth/domain/providers/auth-provider.interface.ts`）で抽象化され、実装は `SupabaseAuthProvider` のみ
- ログイン手段はメール/パスワードのみ。ユーザー登録は招待制（`inviteUserByEmail`）
- DB ユーザー（`User`）は初回セッション確立時に `ExchangeCodeForSessionUsecase` で遅延作成される（role: `user`、テナント紐付けなし。紐付けは管理者が後から実施）
- OAuth の code → session 交換経路（`/api/auth/callback` ルート + `ExchangeCodeForSessionUsecase`）は実装済み
- Supabase Auth は Google をソーシャルプロバイダーとしてネイティブサポートしているため、認証基盤の差し替えは不要。「Supabase Auth の中で Google を有効化する」アプローチを取る

## 決定事項

| 論点 | 決定 |
|---|---|
| 新規ユーザーの扱い | 許可ドメインの Google アカウントなら DB に自動作成（招待フローと同じ遅延作成に乗る）。role は `user`、テナント紐付けは従来どおり管理者が後から設定 |
| プロバイダー切り替え | リスト形式の環境変数 `ADMIN_AUTH_PROVIDERS` で制御。未設定時は従来挙動（パスワードのみ） |
| ドメイン制限の適用範囲 | Google 経由のログインのみに適用。パスワードログイン・招待・リカバリーは制限対象外（後方互換） |

## 環境変数

| 変数名 | 形式 | 未設定時の挙動 | 例 |
|---|---|---|---|
| `ADMIN_AUTH_PROVIDERS` | カンマ区切りリスト。有効値: `password`, `google` | `password` のみ有効（既存挙動） | `password,google` / `google` |
| `AUTH_ALLOWED_EMAIL_DOMAINS` | カンマ区切りリスト（メールドメイン） | 制限なし | `team-mir.ai` |

- どちらもサーバー側でのみ参照する（`NEXT_PUBLIC_` は使わない）。ログインページはサーバーコンポーネントのため、表示制御はサーバー側で完結できる
- `AUTH_ALLOWED_EMAIL_DOMAINS` は Google 経由のセッションにのみ適用する
- 環境変数の読み取りは presentation 層（actions / loaders / route handler）で行い、Usecase へはコンストラクタ経由で注入する（DI ルール準拠）

チームみらい環境の設定値: `ADMIN_AUTH_PROVIDERS=password,google`（移行期間後、必要なら `google` のみに変更可能）、`AUTH_ALLOWED_EMAIL_DOMAINS=team-mir.ai`

## 認証フロー

```
[ログインページ]
  │ 「Google でログイン」ボタン（form action）
  ▼
[action: loginWithGoogle]
  │ LoginWithGoogleUsecase → AuthProvider.signInWithOAuth("google", ...)
  │ Supabase が認可 URL を生成（PKCE。code_verifier は cookie に保存される）
  ▼ redirect
[Google 認証画面]（hd パラメータで team-mir.ai を事前選択 ※UX目的のみ）
  ▼ 認証成功
[Supabase /auth/v1/callback]
  ▼ redirect（?code=...）
[GET /api/auth/callback]
  │ ExchangeCodeForSessionUsecase
  │   1. code → session 交換
  │   2. Google 経由 かつ 許可ドメイン外 → サインアウトしてエラー（DOMAIN_NOT_ALLOWED）
  │   3. DB に User がなければ自動作成（既存ロジック）
  ▼
[/ へリダイレクト]（パスワード設定画面はスキップ）
```

## 変更内容

### Domain 層

**`AuthProvider` インターフェース拡張**（`domain/providers/auth-provider.interface.ts`）

OAuth 認可 URL の取得メソッドを追加する。

```typescript
signInWithOAuth(
  provider: "google",
  options: { redirectTo: string; queryParams?: Record<string, string> },
): Promise<{ url: string }>;
```

**`SupabaseAuthUser` モデル拡張**（`domain/models/supabase-auth-user.ts`）

認証プロバイダー種別を追加する。Supabase の `app_metadata.provider`（`"email"` / `"google"` 等）をマッピングし、ドメイン制限の適用判定とパスワード設定画面スキップ判定に使う。

**ドメイン許可判定モデル（新規）**（`domain/models/allowed-email-domains.ts`）

メールアドレスが許可ドメインに含まれるかを判定する純粋ロジック。単一概念のビジネスルールのため Domain Model に配置し、`interface + const` パターンで実装する。

- 判定仕様: メールアドレスの `@` 以降を小文字比較で照合。許可リストが空（未設定）の場合は常に許可
- `server-only` は含めない（純粋関数のため。ただし現時点でクライアントからの参照予定はない）

**認証プロバイダー設定モデル（新規）**（`domain/models/auth-provider-config.ts`）

`ADMIN_AUTH_PROVIDERS` の値文字列をパースし、有効なプロバイダー一覧を返す純粋ロジック。不明な値は無視し、結果が空なら `["password"]` にフォールバックする（既存挙動の保証）。

**エラーコード追加**（`domain/errors/auth-error.ts`）

既存の `AuthErrorCode` union に以下を追加する。

| コード | 用途 | ユーザー向けメッセージ |
|---|---|---|
| `DOMAIN_NOT_ALLOWED` | 許可ドメイン外のアカウントで Google ログインを試行 | `このメールアドレスのドメインではログインできません` |

エラーハンドリング設計に関する補足:

- auth コンテキストは `AuthError`（単一クラス + `code`）パターンが確立済みのため、これに従う。バックエンドアーキテクチャガイド 6.3.2 の拡張エラー型（`path` / `severity` を持つ形式）は複数エラーを収集して返すバリデーション用途のものであり、認証エラーは常に単一・即時中断（すべて error 相当、warning の概念なし）のため適用しない
- エラーコードは既存同様、大文字スネークケースで `as const` 的に型安全な union として定義する
- OAuth 認可 URL 取得の失敗は既存コード `AUTH_FAILED` / `NETWORK_ERROR` を再利用する（新コードは追加しない）
- Presentation 層では既存の `AUTH_ERROR_MESSAGES` マップでユーザー向けメッセージに変換する

### Application 層

**`LoginWithGoogleUsecase`（新規）**

- `AuthProvider` をコンストラクタ注入
- `execute(redirectTo, allowedDomains)`: `signInWithOAuth` を呼び、認可 URL を返す
- 許可ドメインが 1 件のみの場合、Google の `hd` クエリパラメータに設定する（アカウント選択画面の絞り込み。**UX 改善目的であり、セキュリティ境界ではない**。強制はサーバー側チェックで行う）

**`ExchangeCodeForSessionUsecase`（変更）**

- コンストラクタに許可ドメインリストを追加注入
- code → session 交換後、**セッションのユーザーが Google 経由の場合のみ**ドメイン許可判定を実行。不許可なら `signOut` でセッションを破棄し `DOMAIN_NOT_ALLOWED` を throw する（DB ユーザー作成前に判定する）
- 戻り値の `isNewUser` を `requiresPasswordSetup` に改める。`true` になるのはメール（招待）経由の新規ユーザーのみとし、Google 経由のユーザーは常に `false`（パスワード設定が不要なため）。呼び出し元は callback ルートのみであり、外部互換性の問題はない

### Infrastructure 層

**`SupabaseAuthProvider`（変更）**

- `signInWithOAuth` を実装。サーバー側クライアントで認可 URL を取得して返す（ブラウザリダイレクトは presentation 層の `redirect()` で行う）
- `mapToSupabaseAuthUser` で `app_metadata.provider` をマッピングに追加

### Presentation 層

**`loginWithGoogle` アクション（新規）**（`presentation/actions/login-with-google.ts`）

- `ADMIN_AUTH_PROVIDERS` を検証し、`google` が無効なら `/login` にエラーリダイレクト（URL 直叩き・環境変数変更漏れへの防御）
- `AUTH_ALLOWED_EMAIL_DOMAINS` と `SITE_URL` を読み取り、`LoginWithGoogleUsecase` を組み立てて実行。`redirectTo` は `${SITE_URL}/api/auth/callback`
- 取得した認可 URL へ `redirect()`

**ログインページ / `LoginForm`（変更）**

- ログインページ（サーバーコンポーネント）で `ADMIN_AUTH_PROVIDERS` をパースし、表示するログイン手段を決定して `LoginForm` に渡す
- `password` 有効時のみ: メール/パスワードフォームと「パスワードをお忘れですか」リンクを表示
- `google` 有効時のみ: 「Google でログイン」ボタンを表示（form + server action）
- 両方有効時は区切り線で併記
- UI は shadcn UI コンポーネント（`@/client/components/ui` の index 経由 import）と CSS 変数を使用する（admin UI ガイドライン準拠）

**`/api/auth/callback` ルート（変更）**

- `requiresPasswordSetup` が `true` の場合のみ `/auth/setup` へ、それ以外は `/` へリダイレクト
- `DOMAIN_NOT_ALLOWED` エラー時は `/login?error=...` にユーザー向けメッセージ付きでリダイレクト

**`proxy.ts`（変更）**

- `publicPaths` に `/api/auth/callback` を追加する。OAuth リダイレクトの着地時点では未認証のため、現状のままではログインページへ弾かれてしまう（現状この経路が機能しているのは認証済みセッションが前提のケースのみ）

### 変更しないもの（後方互換性の担保）

- `loginWithPassword` アクション、`LoginUsecase`、招待（`InviteUserUsecase`）・パスワードリセット・リカバリーの各フロー: 一切変更しない
- 招待可能なメールアドレス: ドメイン制限の対象外のまま（外部ドメインの招待は従来どおり可能。招待経由ユーザーはメールプロバイダーのためドメインチェックが適用されない）
- `ADMIN_AUTH_PROVIDERS` / `AUTH_ALLOWED_EMAIL_DOMAINS` とも未設定なら、UI・挙動は現行と完全に同一

## セキュリティ上の考慮

1. **ドメイン制限はサーバー側で強制する**: Google の `hd` パラメータや Supabase 側の設定はバイパス可能性があるため、`ExchangeCodeForSessionUsecase` 内のチェックを唯一の強制ポイントとする。不許可時はセッション破棄まで行い、認証済み状態を残さない
2. **チェックは DB ユーザー作成より前に行う**: 不許可ドメインのユーザーレコードが作られないようにする
3. **`google` 無効時のアクション防御**: UI 非表示だけでなく、`loginWithGoogle` アクション自体がプロバイダー設定を検証する
4. **`/api/auth/callback` の公開範囲**: public 化するのはこのルートのみ。ルート自体は code の交換に失敗すれば `/login` に戻すだけであり、認証をバイパスする経路にはならない

## インフラ・外部設定（リポジトリ外の作業）

1. **Google Cloud Console**: OAuth 2.0 クライアント ID を作成。承認済みリダイレクト URI に Supabase のコールバック URL（`https://<project-ref>.supabase.co/auth/v1/callback`、セルフホストの場合は相当の URL）を登録
2. **Supabase**: Google プロバイダーを有効化し、クライアント ID / シークレットを設定（クラウド版はダッシュボード、セルフホストは `GOTRUE_EXTERNAL_GOOGLE_ENABLED` 等の GoTrue 環境変数）。Redirect URLs の許可リストに `${SITE_URL}/api/auth/callback` を追加
3. **admin のデプロイ環境**: `ADMIN_AUTH_PROVIDERS` / `AUTH_ALLOWED_EMAIL_DOMAINS` を設定

## 動作確認観点

- 環境変数未設定時、ログインページ・全認証フローが現行と同一であること
- `ADMIN_AUTH_PROVIDERS=password,google` で両方のログイン手段が表示され、それぞれでログインできること
- `ADMIN_AUTH_PROVIDERS=google` でパスワードフォームが表示されず、`loginWithPassword` 系フローに影響がないこと
- 許可ドメインの Google アカウントで初回ログイン → DB に role `user` で自動作成され、`/auth/setup` を経由せず `/` に到達すること
- 許可ドメイン外の Google アカウント → `DOMAIN_NOT_ALLOWED` メッセージが表示され、セッション・DB ユーザーが残らないこと
- 招待フロー（外部ドメイン含む）・パスワードリセットフローが従来どおり動作すること
- `pnpm depcruise` でレイヤー依存違反がないこと
